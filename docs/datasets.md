# 训练数据集

本文覆盖两条互不相干的训练线：**阶段 7 的物候/收获预测**（主要篇幅）与
**阶段 2.7 虫害检测的补充数据**（见「阶段 2.7」一节）。两边的数据集、许可与
用途都不一样，别把表格混着读。

## 阶段 7 训练数据集

「我的农田」的收获日预测（`scripts/24_train_harvest_model.py`）最终要吃
**物候观测数据**。下面是候选数据集清单与训练路径。

**现在的状态**：本地那条路（`scripts/24_train_harvest_model.py`）只在
**全平台 `harvest_records` 累计 ≥ 30 条**时才训练（清单 7.3.4 定的阈值）。
样本不够时收获预测自动走纯积温法（`method=gdd_fallback`）—— 这不是没做完，
是设计的等待状态：一个刚部署的平台不可能已经有 30 茬收获记录。

**但本地那条路造不出正确的标签**：库里存的是「收获当天」那一刻的特征快照，
而标签是全生育期总天数，于是 `features["days_since_sow"] ≈ actual_days`，
模型只会学成一个恒等映射；而线上把模型输出当**「从观察日到成熟的剩余天数」**用
（与 `_gdd_interval` 同列取 min/max）。真按那样训出模型，收获日会被系统性推晚。

**一个生长季里要有多个观察截止日**才可能学到那张映射表 —— 光靠本地记录做不到，
外部物候数据集能做到。所以外部数据集这条路（下面第 1 步）不是「锦上添花」，
它是让收获模型真正有用的**正路**，本地那条路只是补充。也因为两边口径不同，
`scripts/24` 见到外部产物会**拒绝覆盖**（除非显式 `--force`）。

### 天气那一步为什么要挂着跑几个小时

**这不是脚本慢，是 Open-Meteo 免费额度的固有节奏。** 一次要 22 年（8035 天）×
3 个变量，这种"重"请求按调用权重的消耗远高于线上那份"近 90 天"，一个小时里
只能发出去几十次。撞上限时服务端回的是：

    HTTP 429（Hourly API request limit exceeded. Please try again in the next hour.）

关键在于**这是「小时」窗口，不是「分钟」**：`--wait-quota` 之外的任何重试节奏都
救不了它 —— 在同一个窗口里怎么试都被拒。所以 `scripts/30` 对三种失败分别处理：

| 失败 | 等待 | 为什么 |
|---|---|---|
| 普通网络失败 | 4 / 8 / 12 秒递增 | 偶发丢包 |
| 429（分钟窗口） | **至少 65 秒** | 等 30 秒穿不过一分钟窗口，只会在窗口边缘连撞两次（实测一个县白耗 96 秒） |
| 429（小时窗口） | 默认**干净退出**；加 `--wait-quota` 则睡到**下一个整点**自动续 | 窗口内重试毫无意义 |

一县一个文件、存在即跳过，所以**中断没有任何代价** —— 睡过头、被关掉、断电，
重跑都是接着拉。四五百个县要分几个整点窗口才拉得完，这是预期行为。

**绝不为省时间而合成天气**：拉不到就让它缺，缺的那一季在第 31 步被丢弃并计数。
用气候平均或邻近县插值补出来的"天气"会让模型在假数据上训练，而报告上看不出来。

### 首次实跑（2026-10-10，只有 21 个县）

天气还没拉全时先跑了一遍，为的是验证**链路**而不是拿分数。结果如实记在这里：

| 留出档 | 模型 MAE | 仅 q50 MAE | 基线 MAE | q10–q90 覆盖率 | 偏差 |
|---|---|---|---|---|---|
| `group`（同分布，上限参考） | 15.66 | 5.70 | 22.22 | 0.718 | +11.27 |
| `time`（train ≤2016） | 24.72 | 6.84 | 31.64 | 0.642 | +20.98 |
| **`province`（留出湖北，闸门）** | **21.08** | **16.44** | **26.25** | **0.414** | **+9.71** |

**闸门未通过**，卡在覆盖率那一条（0.414，要求 0.70–0.90）；MAE、行数、组数三条都过了。

三条结论，都符合预期，都不是代码问题：

1. **覆盖率缺口是域偏移，不是 bug。** 同分布的 `group` 档覆盖率 0.718 已经落在
   合格区间的边缘，而换成"留出湖北省"就掉到 0.414 —— 分位区间是在训练省份上
   标定的，换一个省真实散布更大，区间就显得窄了。训练省份越多（这里只有江苏
   一个省在训），这一档越接近名义的 0.80。

2. **部署口径把模型稀释掉了。** 留出湖北这一档，仅用 q50 的 MAE 是 16.44 天，
   而走完整 `predict_harvest`（积温两端点 ∪ 三个分位取 min/max 再取中点）是
   21.08 天 —— 计划里预判的「架构效应」原样出现。这是 `predict_harvest` 的
   组合方式问题，**不在本次范围内改**，只如实记进
   `outputs/reports/harvest_external_eval.json`。

3. **两个覆盖率（原始 0.414 / 最终 0.307）看着像打架，其实是钳位。**
   `predict_harvest` 组合出候选区间之后，会按 7.3.4 的**宽度控制表**把半宽钳到
   `_half_width_limit(距收获天数)`（`harvest_model.py` 的 width control），
   于是"最终区间"**收窄**在 `most_likely` 两侧 —— 这是有意为之（「精确到某一天」
   是假承诺，区间太宽同样没意义）。所以最终覆盖率**必然低于**模型自己的
   q10–q90 覆盖率，不是 bug。闸门量的是**原始** q10–q90，量的就是"分位有没有
   标定好"；这一条没过，说明分位区间对省外数据**偏窄**（欠离散），
   而这是训练省份太少时该有的样子。

**这个结果是「21 个县」下的结果，不该当成最终结论**：样本量、省份数、年份跨度
都不够。把四五百个县拉全之后重跑 31 → 32 才是有效评估。

### 起点用的是移栽日，不是播种日

数据集给的是**移栽日**，本应用 `field.sow_date` 的语义是**播种** ——
这个口径差**不许**用「减一个育秧天数」去抹平（那是编数据），它被如实记进
`provenance`（`season_start_basis="transplant"`）与报告，也正是闸门必须用
「留出湖北」这一档的原因。

**第 2 步（未做）**：IPK + 油菜数据集补小麦/油菜。本次只做水稻 ——
`CROP_CODES` 被单元测试锁死，新增作物要连带改配置与另一条集合断言。
另外 `ChinaCropPhen1km` 那份是 1 km GeoTIFF（≈9.4 GiB，需要 GDAL/rasterio，
Windows + Py3.11 上难装），本次**不走**这条路。

**第 3 步（未做）**：本地 `harvest_records` 微调。要做对得先在生长季里
**周期性快照特征**（新表 / 新记录），否则标签口径永远是错的 —— 见开头那段。

**独立验证**：第 653 站那份气象站数据（`http://image.data.cma.cn`）用来做外部验证，
**不与训练集混用**。混用会让评估结果虚高，而这种虚高在换一块地之后就消失了。

## 隐私

**训练只提取数值特征，不带 `user_id`、田块名与位置。**

这条不是靠训练脚本自觉遵守的，而是在取数时就切干净了：
`src/farm/repo.py::list_harvest_features()` 的 SQL 只 `SELECT crop, sow_date,
harvest_date, actual_days, gdd_at_harvest, features_json` —— 根本没有把
`user_id` / `field_id` 取出来。另外 `scripts/24_train_harvest_model.py` 里
还有一道断言，一旦样本里出现身份字段就直接中止训练（而不是只打个警告）。

为什么这么严：模型文件是要被拷来拷去的产物。一旦身份字段进了训练集，
它们会以某种形式留在模型里，而**没人会在几个月后还记得去检查那个文件**。

## 阶段 2.7：虫害检测的外部数据集

虫害检测（`scripts/16`–`19`，IP102 / YOLOv8n）只有 18976 张检测图 / 22284 个实例，
低精度有四个原因，其中只有两个跟「数据少」有关：**训练没收敛**（30 轮 mAP50
仍在单调上升，延长训练即可）和**长尾**（5 个类三档全零）。

**所有数据补充方案都撞在同一条硬约束上**：

> **没有任何公开检测数据集使用 IP102 的 102 类物种体系。**
> Pest24 是 24 类、AgriPest 14 类、MPD2018 16 类、AgroPest-12 干脆是
> 「ant / beetle」这种目科级。**硬合并进 102 类就是灌标签噪声**，
> 很可能把现在 0.50 的 mAP 拉低。

所以下面两条路都做了「宁缺毋滥」的设计，且**都不改变 102 类体系**。

| 数据集 | 来源 / 机构 | 许可 | 规模 | 在本项目里的用途 | **是否真的进了训练** |
|---|---|---|---|---|---|
| **IP102 分类集** | Figshare `IP102.zip`（原作者 xpwu95/IP102 的官方镜像之一） | 学术免费；其他用途需联系原作者 | 2.94 GB / 75,226 个归档成员 | **唯一同体系**的补充源。用 `scripts/37` 做 copy-paste 增广，只补**三档合计实例数 < 20** 的 10 个稀有类（含 5 个零实例「死类」） | **尚未**。已生成 584 张（`data/pest_aug/v2/`），只进 train，**还没训** |
| **Pest24** | 中科院合肥智能机械研究所 `http://aisys.iim.ac.cn/zhibao.html` | 研究/非商业 | 25378 张 / 24 类 | 只把 **XML 里零 object** 的图当**纯负样本**（空 label），对准 precision | **否**。见下「为什么 Pest24 没进训练」 |
| Zenodo · COCO 重排版 | `zenodo.org/records/15546285` | CC BY 4.0 | 798 MB | **不用**：重排格式没有原始图片切图语义，copy-paste 需要原图 | 否 |
| Kaggle · `ip102-pest-dataset` | Kaggle | 见数据集页 | 约 3.0 GB | IP102 分类集的备用镜像（本机可达） | 否 |

### 镜像可用性（2026-10-11 本机实测，`scripts/36 --probe`）

| 镜像 | 结果 |
|---|---|
| Figshare `ndownloader.figshare.com/files/62860060` | **HTTP 200，2.94 GB**，响应带 ETag（`1b1764c93380761e7797efaa57b4bda4-3`，多段上传格式）。**已下载并校验通过**：75,226 个成员全量 CRC 通过，sha256 `9a7cd114ca1c2d4a6393ec0d4c1ff6525471d63286d2bff983eec816a9f24a3f` |
| Kaggle `api/v1/datasets/download/...` | **HTTP 200，2.94 GB**，响应带 32 位 MD5（`d8b997dcb6f68430642e22bdadef106c`）—— 可直接当钉值 |
| Zenodo | 本机 DNS 解析失败（`getaddrinfo failed`） |

计划原先担心「IP102 走网盘、没有稳定 file id，所以 sha256 钉不住」—— **实测下来这个担
心对 Figshare 不成立**：直链稳定且响应带摘要。真正钉不住的是网盘临时链，那种情况下
`checksums.json` 里的 sha256 只能证明「每次下到的是同一份」，不代表来源未变，
这一区分写在了 `data/pest_cls_raw/checksums.json` 的 `mode` 字段里。

### 为什么 Pest24 没进训练

`scripts/38 --probe` 在本机实测：`aisys.iim.ac.cn:80` **连接超时**
（域名解析成功、TCP 握手超时，即服务不可达而非 DNS 问题）。按计划约定，
探不到就整档停下、**如实报告、不绕过、不合成替代数据**。

要补这一档，需人工在浏览器里打开上述站点按页面说明申请/下载，然后：

```powershell
python scripts/38_download_pest24.py --archive <下载到的档案>
python scripts/39_build_pest_mixed.py --ratio 0.15
```

**负样本的取舍规则**（这一档的核心决策）：只有 XML 里**一个 object 都没有**的图
才够格当负样本。理由有两条，方向相反但都指向「只取零物体图」——

- **有能映射到 IP102 的物体** → 不能当负样本（等于教模型「看到该虫就闭嘴」，直接压 recall）；
- **物体全都不可映射** → 也不能当负样本（Pest24 按设计整份都是虫害图，「我的类名表没覆盖它」
  **不等于**「图上没虫」，当负样本同样是假负）。

这条规则的好处是**完全不依赖类名映射表**，也就不依赖任何无法核实的东西。

### 类序核对：102 类逐条对齐（本档的命门，已通过）

IP102 分类集的 `classes.txt` 每行是「1 起的序号 + 名字」（`1  rice leaf roller`），
而权威表来自 16 号脚本的 `PESTYOLO_CLASSES`（只有名字）。脚本剥掉序号前缀后逐条比对，
**结果：102/102 行剥前缀后与权威表逐字相同（写法差异 0 处）**。

剥前缀**不等于**放宽比对 —— 它同时要求序号与行号逐位自洽（第 i 行的序号必须是 i 或 i+1），
所以「序号对、行序乱」的文件仍会被中止。这条守卫是必要的：整表错一位不会报错，
只会让每个稀有类拿到**别的虫**的监督信号，而报告上一点异常都看不出来。

解压后的结构是 `extracted/classification/{train,val,test}/<0..101>/` —— **数字化目录是 0 起的，
与检测集下标同基**（`index_base=0`）。三个划分各有一份 102 个类目录，脚本确定性地取 `train`
那一份，并把另外两个候选写进 `layout.json`（旧版取「目录最多的父目录」，三方并列时
等于随机挑一个且不记录）。

| 类 | 三档合计 | val+test 实例数 | 能不能量到 AP |
|---|---|---|---|
| 59 / 60 / 63 / 75 / 80 | 0 | **0** | **测不了**（AP 在零分母上无非定义） |
| 61 | 2 | 1 | 名义可测，实际是二值噪声 |
| 52 / 72 / 91 / 98 | 5~13 | 2~5 | 名义可测，分母太小 |

所以第二档的正当性**不是「能涨分」**，而是：这 5 个类现在拿不到任何监督信号，
而没有任何别的公开数据集能给它们同物种、同体系（102 类）的监督。
**报告里不会把「没涨分」粉饰成别的说法。**

### 一个没做到的检查：产物外观没验

`data/pest_aug/v2/` 的 584 张图只验了**结构不变量**（584 图 ↔ 584 标签、每张都带目标类的框、
坐标不越界、无 NaN、彼此无重复、与 val/test 无重复、新贴框面积 0.0075~0.1193 落在目标区间）。
**贴上去的东西「长得像不像那只虫」没有验过** —— 本机的图片渲染在本会话里不可用
（连 2.5 KB 的测试 PNG 都读不出来）。挡住「贴了一片叶子当虫」的只有那两道占比门槛
与「取 GrabCut 最大连通域」，这是一个已知的、未被视觉确认的残余风险。

## 关于「现在能不能训」

跑 `python scripts/24_train_harvest_model.py` 会先打印当前样本数。
不足 30 条时它**不会硬训**，会告诉你还差多少、然后正常退出
（退出码 0 —— 这是等待状态，不是错误）。

想先看看训练链路通不通，可以用 `--force` 强制训练，但产出的模型不可信，
不要把结果写进任何报告。
